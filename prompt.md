## 2. THE HARD PROBLEM, STATED FIRST
The hardest problem in offline settlement is the double-spend: two merchants accept payment from the same offline balance while partitioned.

**Guarantees & Non-Guarantees:**
The system guarantees eventual consistency and cryptographically verifiable transaction origination. It explicitly DOES NOT guarantee synchronous finality; offline transactions carry inherent counterparty risk.

**Conflict Detection:**
When two transactions spending the same merchant balance meet in the mesh, they are detected by comparing the merchant's Ed25519 public key and the monotonic transaction nonce.

**Deterministic Resolution Rule:**
If nonces collide (a double spend), the transaction with the mathematically lowest BLAKE3 hash of its signature bytes wins. This rule requires no coordination and behaves identically on every device.

**The Losing Transaction:**
The losing transaction is dropped from the local mempool. A `SettlementFailed` gossip message is generated by the node that detected the conflict and routed back to the originating merchant. The merchant's POS UI will flag the payment as voided.

**Offline Exposure Limits (Risk Bounding):**
The risk is bounded, not eliminated. The daemon enforces a hard local cap: it will reject and refuse to route any offline transactions from a single merchant public key if their total unsettled offline volume in the local database exceeds 500 USDC. This bounds the maximum double-spend damage per mesh partition to 500 USDC.

**Escalation:**
If a sophisticated attacker bypasses local limits by maintaining strict physical partitions until settlement, the conflict is escalated to the HaloPay API. The API will reject the second transaction on-chain. The mesh nodes do not paper over this; they accept the API rejection and propagate the failure back to the UI.

## 3. PROTOCOL SPECIFICATION
**Message Types:**
1. `Hello`: Sent every 5 seconds to announce presence.
2. `TxGossip`: Sent when a new transaction is generated or received.
3. `SettlementAck`: Sent when a node successfully anchors a batch to the internet.

**Byte Layout (Binary, Little Endian):**
*   `Version` (1 byte): Must be `0x01`.
*   `Type` (1 byte): `0x00` (Hello), `0x01` (TxGossip), `0x02` (SettlementAck).
*   `SenderPubKey` (32 bytes): Ed25519 public key.
*   `Timestamp` (8 bytes): Unix epoch seconds.
*   `Signature` (64 bytes): Ed25519 signature over the Payload.
*   `PayloadLength` (2 bytes): Size of payload.
*   `Payload` (N bytes): ChaCha20-Poly1305 encrypted JSON data.

**Maximum Message Size & Fragmentation:**
The maximum size is 256 bytes due to BLE constraints. If a payload exceeds this, the `Type` byte is OR'd with `0x80` to indicate fragmentation. The `Payload` is prefixed with `ChunkIndex` (1 byte) and `TotalChunks` (1 byte). The receiving node holds chunks in memory until reassembled.

**Gossip Mechanics:**
The network uses Flood Routing. When a node receives a `TxGossip` message, it hashes the payload. It checks an in-memory Least Recently Used (LRU) cache (max 10,000 entries). If the hash exists, it is a duplicate and dropped. If it is new, it is added to the cache, written to disk, and broadcast to all currently connected peers except the sender.

**Versioning:**
If a device encounters a `Version` byte other than `0x01`, it drops the message immediately and closes the connection to that peer.

**Timing Parameters:**
*   `Hello` broadcast interval: 5,000 ms.
*   Peer timeout (considered dead): 15,000 ms.
*   Gossip backoff: 50 ms delay between broadcasting fragments to prevent radio buffer overflows.

## 4. CRYPTOGRAPHIC DESIGN
**Primitives:**
*   **Signing:** `Ed25519` (Curve25519).
*   **Encryption:** `ChaCha20-Poly1305` (AEAD).
*   **Hashing:** `BLAKE3`.

**Verification:**
The sender signs the `Timestamp` + `PayloadLength` + `Payload` bytes. The receiving device verifies the `Signature` against the `SenderPubKey` before deserializing the payload.

**Device Identity & Trust:**
Identity is the `Ed25519` public key. Generated on first run and stored in `~/.halopay/node.key`. The network uses Trust On First Use (TOFU). Any device can join the mesh and route packets.

**Replay Protection:**
The 8-byte `Timestamp` acts as the nonce. The receiving device maintains a rolling window of `+/- 300 seconds` (5 minutes) from its local clock. Any message outside this window is immediately dropped.

**Security Boundaries:**
*   **Eavesdropper:** An attacker sniffing BLE can learn the mesh size and traffic volume (number of packets). They CANNOT learn transaction amounts, sender IDs, or receiver IDs because the `Payload` is AEAD encrypted.
*   **Malicious Node:** A bad actor in the mesh CAN drop packets (censorship) but CANNOT forge transactions, alter amounts, or impersonate merchants because they cannot forge the Ed25519 signature.

## 8. LOCAL PERSISTENCE
The daemon must survive battery death.

**Format and Timing:**
Data is written to `~/.halopay/mesh.db` (SQLite) synchronously the moment a valid `TxGossip` signature is verified, before forwarding to peers.

**Schema:**
`CREATE TABLE txs (hash TEXT PRIMARY KEY, payload BLOB, status TEXT, added_at INTEGER);`

**Safety & Bounds:**
Every insert uses a SQLite transaction. If the device dies mid-write, SQLite rolls back automatically. Storage is bounded by deleting the oldest rows where `status = 'settled'` if the database exceeds 50MB.

**Startup Replay:**
On startup, the daemon queries `SELECT * FROM txs WHERE status = 'pending'`. These are loaded into memory and immediately queued for gossip rebroadcast.

## 9. SETTLEMENT PATH
**Detection:**
The `settlement.rs` module runs a background task executing HTTP GET `https://api.halopay.app/ping` every 60 seconds. If it receives `200 OK`, connectivity is established.

**Submission:**
The device queries all `pending` transactions from SQLite. It sends an HTTP POST to `https://api.halopay.app/settle` containing a JSON array of base64 encoded transaction payloads.

**Simultaneous Submit & Idempotency:**
If multiple nodes regain connectivity and submit the same batch, the HaloPay API enforces idempotency using the BLAKE3 transaction hash. The first request processes the funds; the subsequent requests return `200 OK` (Acknowledged as already settled).

**Partial Success:**
The API returns JSON: `{"settled": ["hash1", "hash2"], "rejected": ["hash3"]}`. 

**Back-Propagation:**
The node updates its SQLite DB, marking hash1/hash2 as `settled` and hash3 as `failed`. It constructs a `SettlementAck` message for each and gossips it back into the offline mesh so other devices can purge their queues.
